# Pre-registration — AIXL 0.3 Semantic Core (written 2026-09-26 BEFORE building or measuring anything)
Hypothesis (H1, from the spec): two different expressions can converge to the same semantic representation, and two similar expressions can be detected as semantically different — as a computable, evaluable function.
Experiment: 200 pairs (100 EQUIVALENT + 100 NOT_EQUIVALENT), authored BLIND by independent model agents (Sonnet ×2) who see only the domain vocabulary and the labelling rule, never the code. Plus 40 blind items for ambiguity/contradiction (agent C). Plus my own 200-case dev benchmark (same author as the code; NOT the headline number).
First run of the code on the blind set is recorded BEFORE any tuning; anything fixed afterwards is reported as contaminated.
Success criteria (spec §42, treated as experimental targets, not truths), on the BLIND 200 pairs:
 S1. Equivalence accuracy ≥ 90 % (positive class = EQUIVALENT); precision, recall, F1, FP rate and FN rate reported.
 S2. Drift detection ≥ 90 % on the CRITICAL subset of NOT_EQUIVALENT pairs (differences in negation, quantity, time, constraint, reference): a pair counts as detected if it is classified NOT_EQUIVALENT with drift level ≥ MAJOR.
 S3. Preservation ≥ 95 % of negation, quantity, time, constraint, reference through text → graph → AIXL → graph on the blind texts (canonical form unchanged).
 S4 (extra, spec §33): ambiguity accuracy and contradiction accuracy on the blind 40 items, reported without a threshold.
Also reported: compression (chars, bytes, words; LLM tokens only if a real tokenizer is installed — otherwise "not measured"), latency per compare.
Interpretation rule: labels come from the blind authors (single annotator each, no adjudication); disagreements between their label and the code are listed and read by me before I call any of them a code error or a label error, and that reading is stated as such.
Limits declared in advance: rule-based translator with a fixed vocabulary; authors were given that vocabulary, so out-of-vocabulary language is not tested; flat frame (no per-action target pairing) — swaps like "delete users and analyze reports" vs "delete reports and analyze users" are a KNOWN blind spot and will be reported as such if present.

## Experiment E-DATE (date/time/duration extensions + priority-synonym verdict), pre-registered 2026-09-27T13:04:43Z — before set 7 exists
Goal: close the residual gaps E-CODEC left on set 6 (all found in the LLM route's 6 misses; the rule-based route's own false positive on clock times was found while investigating, not part of the original 6) and confirm on a fresh, never-seen set. Frozen code sha256 25613d30c4fd57ba65c8 (was 99ccdcd9f79d734b44e3), card unchanged sha256 8b2b03bf4989a64c9591. Changes made (all in `aixl/translators/natural_to_semantic.py`, none touch the codec/wire format):
1. **Reference clock**: TODAY/YESTERDAY/TOMORROW resolve to an ISO day, THIS_MONTH/LAST_MONTH/NEXT_MONTH to `YYYY-MM`, THIS_YEAR/LAST_YEAR/NEXT_YEAR to a year, against a `today` parameter (`to_graph(text, today=...)`, defaults to the real system date; tests pin a fixed date). Decision verified against the corpus, not guessed: blind3 A3-024, set6 S6-009 and S6-061 are three independent blind-authored pairs across different rounds that all label relative-vs-absolute same-day/month EQUIVALENT — the majority reading. Week-granularity words (THIS_WEEK/LAST_WEEK/NEXT_WEEK) are deliberately left unresolved (no week-range literal in AIXL without inventing one).
2. **Date ranges**: DD/MM/YYYY slash dates (previously not understood at all) and "el N al M de MES de AÑO" (previously only kept the second day) now both resolve to the same two ISO dates.
3. **Clock time**: `antes de`/`before`/`después de`/`after` + a 12h (am/pm) or 24h time now produces a `BEFORE=`/`AFTER=` constraint (already a CRITICAL-severity key). Before this fix the time of day was silently dropped — which was a worse bug than a missed pair: it made two genuinely different deadlines ("before 3pm" vs "before 5pm") compare as a **false EQUIVALENT**, found while investigating S6-076, not part of the original miss list.
4. **Age/duration**: "older than N year(s)" / "más de N año(s) de antigüedad" (also month/day units) → `K:AGE>N:UNIT`; "newer than" / "menos de...antigüedad" → `<`.
5. **Priority synonym ("urgent" vs "high priority")**: verified against the corpus rather than changed — 23 independent blind pairs across 6 rounds label them NOT_EQUIVALENT, only 1 (set6 S6-033, single annotator) calls them equivalent. Left as NOT_EQUIVALENT (no code change); S6-033 stays an open, documented single-annotator disagreement, not "fixed".

### E-DATE round 2 (found while measuring set 7; declared before set 8 exists)
Set 7's Sonnet accuracy (80.0 %) was far below round-1 expectations. Root cause: the reference-clock resolution from round 1 lived only in `aixl/translators/natural_to_semantic.py` (the rule-based translator), so it never touched TIME nodes decoded from an LLM's own AIXL line — an LLM-encoded `T:TODAY` could never match a literal date. Fix: moved the resolution into `SemanticGraph.canonical()` (`aixl/core/ontology.resolve_relative_time_token`, called from `canonical(today=...)`, threaded through `compare_graphs(..., today=...)`), so it applies at comparison time regardless of which route produced the TIME node. Also added a duration-unit normalization (`aixl/core/semantic_graph._unit_canon`): any `:YEAR(S)`/`:MONTH(S)` suffix on a numeric constraint or condition converts to a MONTHS count, so "1 year" and "12 months" compare equal whether written as the AGE constraint or reused as the card's own COUNT>N:UNIT pattern (which is what Sonnet did on its own for S7-077). New code sha256: 20a1edaa23f502f8b844 (was 25613d30c4fd57ba65c8). Regression tests: `test_bug023`–`test_bug028` updated/added (108/108 total).

## Experiment E-INTEROP (cross-vendor ENCODING consistency, not judge accuracy), pre-registered 2026-09-29T15:28:51Z
Goal: every prior cross-vendor experiment (E-XV, E-DATE) measured whether the comparator correctly JUDGES pre-written pairs as equivalent/not — it never measured whether two independent vendor encoders, given the SAME natural-language text and the SAME card, converge on AIXL that compares as equivalent to each other. That is the actual interoperability claim ("can Agent-Sonnet and Agent-Gemini understand each other via AIXL"), and it has never been tested. Frozen: code sha256 d4a740dca1aed42ecd5e, card sha256 1cf27968c1cbbdd934de (both unchanged since E-DATE's final result on 2026-09-27).
Texts: the 100 "side a" texts of blind set 9 (`data/blind9/pairs_S9.jsonl`, already existing, natural, diverse ES/EN/PT, all categories) — reused as STANDALONE inputs; their original pairing/labels are irrelevant here, only the text matters. Encoders: (a) Sonnet 5 — reused verbatim from `data/xv/answers9_sonnet.txt` (already encoded blind, no code access, frozen card, single pass — no new query needed); (b) Gemini (desktop app, same procedure as E-XV/E-CODEC) — encoded fresh for this experiment, blind (no code access), frozen card, single pass. For each of the 100 texts, `compare_graphs(sonnet_i, gemini_i)` is computed once. Metric: cross-vendor consistency rate = fraction judged EQUIVALENT (no gold label involved — this is agreement between two independent encoders, not accuracy against a label). Secondary: for disagreements, which canonical dimension differs (intent/actions/entities/time/constraints/...) and at what drift severity, to diagnose WHERE two vendors' readings of the same card diverge.
No criterion was pre-set for this exploratory measurement (first time it's been done); the number is reported as-is, with the caveat that <100% does not necessarily mean either encoding is "wrong" — it means two independently-encoding agents would NOT currently recognize each other's AIXL as the same request, which is the real-world interoperability risk this experiment exists to quantify.

### E-INTEROP — RESULTS (single run, code sha256 3803e88e628ae5d161d5 [crash-fix applied mid-run, see below], card sha256 1cf27968c1cbbdd934de unchanged)
100 standalone texts (blind9's "side a", reused), each encoded once by Sonnet (reused from `data/xv/answers9_sonnet.txt`, no new query) and once by Gemini (fresh, desktop app, blind, same card). **Cross-vendor consistency: 53/100 (53.0 %)** — the two vendors, given the identical text and the identical card, produce AIXL that the comparator judges equivalent only about half the time. This is a fundamentally different number from E-XV's 93.5–96.5 % (which measured judge ACCURACY against a human label using various encoders one at a time) — no prior experiment had measured whether two encoders agree WITH EACH OTHER.
Mid-run finding: Gemini wrote `A:ANALYSIS` (a noun) instead of `A:ANALYZE` on one line (t020); `derive_intent`'s bare dict lookup raised an uncaught `KeyError`, crashing the entire batch instead of judging that one line correctly. Fixed (`ACTION_TO_INTENT.get(main, "UNKNOWN")`) — a protocol must degrade gracefully on an unrecognized value, not crash. Regression test `test_bug032`. This was a code robustness fix, not a scope change to the measurement (re-run gave the same 53/100 once the crash was fixed).
Disagreement breakdown (47 non-equivalent, of which 19 CRITICAL / 18 MAJOR / 10 MODERATE drift): the single largest driver (18/47, 38%) is a genuine PROTOCOL AMBIGUITY, not a code bug: when the sentence's verb is not literally one of the card's listed actions ("export", "notify", "close [a ticket]", "limit", "present [as a table]"), Sonnet consistently falls back to `I:UNKNOWN` (the literal reading of the card's "no action -> UNKNOWN" rule), while Gemini consistently GUESSES the semantically-closest known action instead ("notify"->SEND, "close"->DELETE, "export"->RETRIEVE, "present a summary"->SUMMARIZE) — both are internally consistent, defensible readings of the SAME card text, and they systematically diverge. The remaining 29/47 are verb-choice disagreements WITHIN the shared vocabulary itself (e.g. "update" -> UPDATE vs EXECUTE, "examine" -> CHECK vs ANALYZE, "generate a summary" -> GENERATE vs SUMMARIZE) plus minor entity/data-extraction differences (an extra/missing `D:REPORT`, `E:RESULT`, etc). No fix applied to either pattern — this is a protocol-design decision (how strict should the closed vocabulary be, and which verb wins for a given synonym), reported to the user for a call, not made unilaterally.
Result file (read-only): `BENCHMARK/results_interop1_FIRST_RUN.txt`. Raw answers: `data/interop/sonnet_answers.txt`, `data/interop/gemini_answers_raw.txt` (both read-only). Reproduce: `python -m benchmarks.interop_eval`.

### E-INTEROP round 2 (option 3 chosen by the user: expand the shared vocabulary + a deterministic tie-break rule), pre-registered 2026-09-29T15:54:37Z

## Experiment E-NEGOTIATE (live negotiation protocol), 2026-09-30 — built at the user's request after E-INTEROP
Goal: E-INTEROP closed cross-vendor encoding consistency from 53 % to 79 % over 3 rounds of shared vocabulary, then hit diminishing returns; the honest conclusion was that closing the rest needs either more narrow-case chasing or "a live negotiation/clarification protocol between agents (AIXL 0.3 has the error codes for it — E002, E007 — but no actual exchange mechanism)". The user asked to build that mechanism.
Design (`aixl/negotiation.py`): a NEW, separate wire format (`NEGOTIATE X=<type> MSG=<id> ...`), not new AIXL atoms — a negotiation turn CARRIES a normal AIXL line as payload where relevant, decoded by the untouched, frozen `aixl_codec`; this keeps the semantic core and the negotiation/transport layer separate. Turn types: REQUEST, CLARIFY, ANSWER, ACCEPT, REJECT. Mechanism: bounded rounds (a cap, never an infinite loop); each round negotiates the SINGLE worst-severity remaining disagreement (CRITICAL before MAJOR before MODERATE before MINOR) so the most consequential difference is resolved first and, if the round cap is hit, what's left unresolved is the least severe; the sender (holder of the original instruction) is trusted for the disputed dimension's value each round; ends in an honest ACCEPT (converged) or REJECT (remaining differences reported, never a silent guess).
Bug found and fixed via REAL DATA before trusting the result (not by unit tests, which all happened to leave a spare round): running `negotiate()` on the 21 real E-INTEROP round-3 disagreements with `max_rounds` set to exactly the number of differing dimensions — the natural way to size the cap — reported 0/21 converged, because the round that patches the LAST dimension was never re-checked for equivalence before falling through to REJECT. Fixed; regression test `test_negotiate_accepts_when_last_round_exactly_resolves_at_the_cap`.
**Real-data measurement** (`benchmarks/negotiation_eval.py`, reusing the genuine Sonnet-vs-Gemini E-INTEROP round-3 disagreements, not synthetic examples): 21/21 real disagreements converge, average 1.14 rounds, max 2 rounds. Caveat stated plainly: this is a designed trust rule (receiver always adopts the sender's value for the disputed dimension), not a discovery of truth — it formalizes "ask the party who holds the original instruction" instead of silently guessing or crashing; convergence is architecturally guaranteed given enough rounds, the real value is the bounded, severity-ordered, honestly-reportable structure around that.
**Live demo with two independent models** (`data/negotiation/live_demo_transcript.md`): two separate Sonnet subagents, each given ONLY the protocol spec document (no code access, no visibility into each other), played receiver and sender roles on a real E-INTEROP disagreement (t013, "Update today's inventory report.", D:REPORT vs D:REPORT,DATA). First attempt exposed a genuine spec bug (a multi-value candidate's own comma collided with the candidates-list separator, producing an ambiguous parse — `;` now separates candidates, `,` stays free inside one). Fixed, re-run: the 3-line exchange (REQUEST/CLARIFY/ANSWER) is the literal, unedited output of the two model calls, and all 3 lines decode cleanly with the real `negotiation.decode()`; the sender's ANSWER correctly re-derived `REPORT` from the original text.
Regression tests: `tests/test_negotiation.py` (12 tests, including the round-cap bug and the semicolon-candidates fix). 125/125 total. Code sha256: 72740c38c2d589c885ad.
