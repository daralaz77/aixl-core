# AIXL 0.3 — Benchmark (methodology and results)

**Labels used in this document.** `DEMO` = written by the code's author, illustrates behaviour. `EVIDENCE` = independent blind authors (model agents that never saw the code), evaluated once before any tuning on that set. `NOT VALIDATED` = no real-world validation exists. Everything is pre-registered in `BENCHMARK/PREREG_0.3.md` (criteria, freeze hashes, and the rules that were added after each run).

## 1. Sets
| Set | What | Authors | Status |
|---|---|---|---|
| `data/dev200.jsonl` (220 cases) | spec §30 schema, 10 categories | me (same as the code) | DEMO/dev |
| `data/blind` (200 pairs + 40 items) | 100 EQ + 100 NEQ; ambiguity 20; contradiction 20 | 3 Sonnet agents, no code access | first run = EVIDENCE; later runs CONTAMINATED |

## 2. Headline: equivalence accuracy on FRESH blind sets (first run only)
Positive class = EQUIVALENT. Criteria (spec §42, treated as experimental targets): S1 accuracy ≥ 90 %, S2 critical-drift detection ≥ 90 %.

| Route | Set | Accuracy | Precision | Recall | F1 | FP | FN | Critical drift (S2) |
|---|---|---|---|---|---|---|---|---|
| rule-based translator | 1 (before any fix) | 72.0 % | 87.9 % | 51 % | 0.646 | 7 | 49 | 89.6 % (60/67) |
| rule-based | 2 (after fixes from set 1) | 80.0 % | 95.5 % | 63 % | 0.759 | 3 | 37 | 97.0 % (65/67) |
| rule-based | 3 (after fixes from sets 1–2) | 76.0 % | 91.9 % | 57 % | 0.704 | 5 | 43 | 91.8 % (56/61) |
| rule-based | 4 (after fixes from sets 1–3) | 76.0 % | 90.6 % | 58 % | 0.707 | 6 | 42 | 92.1 % (58/63) |
| **LLM translator (Haiku 4.5) + core** | **4 (fresh)** | **96.0 %** | 97.9 % | 94 % | 0.959 | 2 | 6 | 96.8 % (61/63) |
| **LLM translator (Sonnet 5) + core** | **4 (fresh)** | **96.5 %** | 97.9 % | 95 % | 0.965 | 2 | 5 | 96.8 % (61/63) |
| LLM (Haiku) + core | 3 (card extension written after reading rule-based failures) | 91.0 % | 98.8 % | 83 % | 0.902 | 1 | 17 | 95.1 %; 18 unparsable lines |
| LLM (Sonnet) + core | 3 (same caveat) | 95.5 % | 100 % | 91 % | 0.953 | 0 | 9 | 100 % |

**Interpretation (INTERPRETATION, not fact).** (1) The rule-based route does NOT reach S1 on unseen phrasing: accuracy plateaus at 76–80 % over three consecutive fresh sets even though ~50 gaps were fixed after sets 1 and 2; each new set brings a new long tail. Its precision is high (≥ 88 %), i.e. when it says "equivalent" it is usually right; recall is the problem (it misses paraphrases). (2) S2 (critical drift) is met by both routes except on set 1 (89.6 %). (3) Feeding the SAME deterministic core (graph, normalizer, comparator, drift) with AIXL produced by an LLM following `data/llm_translator/card_0.3.md` reaches 96 % on a fresh set (S1 met): the core is not the bottleneck; the translator is. (4) Caveats that limit this claim: authors and encoders are all Anthropic models (correlated notion of equivalence; no GPT/Gemini/open-source encoder tested); one pass per model; card extension written knowing failure *classes* seen on sets 1–3 (not set 4 sentences); labels unadjudicated; n = 200 pairs per set (95 % CI for an accuracy of 96 % is roughly ±3 pts).

## 5. Multi-model design (spec §35)
`MODEL → translator → AIXL → codec → SemanticGraph → Comparator`. Any model that can emit AIXL following `card_0.3.md` plugs in through `benchmarks/llm_translator_eval.py` (answers file per model). Measured so far: Haiku 4.5, Sonnet 5. **Not measured: GPT, Gemini, Llama, Mistral.**

## 6. Learning-curve / self-deception log
* Set 1 first run failed S1 (72 %). I fixed what I read, and the fixed system scored 95.5 % on the same set (contaminated, meaningless) but only 80 % on fresh set 2. Repeating the loop gave 76 % on set 3 and 76 % on set 4. The honest generalization estimate for the rule-based translator is therefore ≈ 76–80 %.
* The dev-200 100 % and the six demos must not be quoted as performance.
* E-DATE round 1 (set 6 → date/time/duration fixes) put the reference-clock resolution ONLY in the rule-based translator. Round 2 (set 7) showed this left the LLM route unable to match `T:TODAY` against a literal date at all (Sonnet accuracy on set 7 was 80 %, well below the 94–96 % seen on sets 4–6) — the resolution belonged in `SemanticGraph.canonical()` (comparison time), not the translator. Moved it there; set 7 (re-measured on the SAME already-seen answers, not fresh evidence) went 80 % → 87 %. A further duration-unit fix (1 year = 12 months) found from set 7's remaining misses took it to 88 %. Both fixes were then confirmed on a genuinely fresh set 8 before being reported as evidence (see E-DATE results below) — set 7's post-hoc numbers are a debugging trace, not a claim.

## 7. Cross-vendor test E-XV (set 5, 2026-09-27)
Removes the main threat to the LLM-route result (authors and encoders were all Anthropic). 200 pairs authored by Gemini and ChatGPT; encoders: Haiku 4.5, Sonnet 5, Gemini, ChatGPT (free web) with the frozen card, plus the frozen rule-based code. Accuracy: Haiku 96.5 %, Sonnet 96.5 %, Gemini 95.0 %, ChatGPT 93.5 %, rule-based 78.5 %. Critical drift 58–61 of 61 for every route. S1 met by all LLM encoders, not by the rule-based route. Full table, caveats and parse-failure analysis: `BENCHMARK/PREREG_0.3.md` (E-XV results). Reproduce: `python -m benchmarks.xv_eval rule` / `python -m benchmarks.xv_eval <name> data/xv/answers5/<name>_{1,2,3,4}.txt`.

## 8. Codec-fix confirmation E-CODEC (set 6, 2026-09-27)
After E-XV surfaced 26/1600 (1.6 %) LLM answers that failed to parse, three codec tolerance fixes were made (`O:` as a list atom, stray space after a comparator, repeated list-atom letters merged) — see LIMITATIONS.md. Re-measured on a brand-new blind set (100 pairs, never seen before): Sonnet 5 as LLM translator 94.0 % accuracy, 0 parse failures (rule-based baseline 81.0 %, also 0 parse failures — expected, the rule-based route never emitted the offending patterns). Full table and residual (non-codec) misses: `BENCHMARK/PREREG_0.3.md` (E-CODEC results). Reproduce: `python -m benchmarks.set6_eval rule` / `python -m benchmarks.set6_eval sonnet data/xv/answers6_sonnet.txt`.

## 9. Date/time/duration/reference fixes E-DATE (sets 6-9, 2026-09-27)
Closed the residual gaps E-CODEC left on set 6, across 3 iteration rounds (each round's fixes verified only on the SAME set they were found on, then confirmed on the next fresh set before being trusted — see §6 for the honest trace): (1) reference clock (relative day/month/year resolve against a reference date, moved to `SemanticGraph.canonical()` so it covers both the rule-based AND LLM routes — round 1 put it only in the translator, which round 2 showed was insufficient for LLM-decoded graphs); (2) date ranges (DD/MM/YYYY, two-day-one-month-year phrasing); (3) clock-time BEFORE=/AFTER=/TIME_AT= constraints (12h↔24h), closing a real false-EQUIVALENT for two different deadlines; (4) AGE/duration constraint with year↔month unit conversion; (5) bare-number references ("ticket número 77" = "#77"); (6) the LLM-facing card was updated to teach AGE=/TIME_AT=/bare-number-reference (round 3 — the frozen card from E-XV/E-CODEC had never taught these, which was silently dropping information on the LLM route, a worse bug than a miss). Priority synonyms ("urgent" vs "high priority") were checked against the corpus (23 pairs across 6 rounds say NOT_EQUIVALENT, 1 says EQUIVALENT) and deliberately left unchanged. Final result on set 9 (fresh, never seen, code+card frozen): **Sonnet 95.0 % accuracy, 0 parse failures, 39/39 critical drift**; rule-based 88.0 % (still short of S1, consistent with the standing finding that the rule-based route does not generalize). Full round-by-round trace, remaining known gaps (weekday-relative dates, LLM literal-text quoting of unrecognized clauses) and reproduction commands: `BENCHMARK/PREREG_0.3.md` (E-DATE final result) and `LIMITATIONS.md`.

## 10. Cross-vendor ENCODING consistency E-INTEROP (2026-09-29)
Every prior cross-vendor experiment measured whether the comparator judges pre-written, pre-labelled pairs correctly. None measured whether two independent vendor encoders, given the SAME text and the SAME card, converge on AIXL that they'd recognize as each other's. This is the actual interoperability claim, and it had never been tested. Result on 100 standalone texts (Sonnet + Gemini, single pass each, frozen code+card): **53 % cross-vendor consistency** at baseline — sharply lower than the 93.5–96.5 % judge-accuracy numbers, because that's a different question. Root cause of 38 % of the disagreements: a genuine protocol ambiguity (not a bug) — Sonnet defaults unrecognized verbs to `I:UNKNOWN`, Gemini guesses the closest known action instead. A real crash bug was found and fixed along the way (`derive_intent` raised on an out-of-vocabulary action value instead of degrading gracefully — `test_bug032`).
The user chose to close this gap with a shared, explicit, deterministic vocabulary (the only real "way to reach agreement" for two parties that never talk live): 3 bounded rounds (a much bigger VERB TABLE covering ~40 new EN/ES/PT synonyms, a tie-break rule for generic-verb-vs-specific-object ambiguity, then narrowing that rule and fixing 2 more gaps it exposed) took cross-vendor consistency **53 % → 69 % → 79 %**, with 0 parse failures by round 3 (`test_bug033`). Full round-by-round breakdown and the honest "not chased further" call: `BENCHMARK/PREREG_0.3.md` (E-INTEROP final result) and `LIMITATIONS.md`. Reproduce: `python -m benchmarks.interop_eval` (round 1) or decode+compare `data/interop/{sonnet,gemini}_answers_round3.txt` (final round).

## 11. Live negotiation protocol E-NEGOTIATE (2026-09-30)
Built at the user's request after E-INTEROP: a bounded clarification exchange (`aixl/negotiation.py`) so two agents that disagree don't silently guess or crash. New wire format (`NEGOTIATE X=REQUEST|CLARIFY|ANSWER|ACCEPT|REJECT ...`), separate from AIXL's own atoms; each round resolves the single worst-severity disagreement first; the sender (holder of the original instruction) is trusted for that one dimension; ends in an honest ACCEPT or REJECT, never an infinite loop. A real bug (round-cap off-by-one) was found by running it on genuine data, not caught by unit tests alone. Measured on the real 21 E-INTEROP disagreements: **21/21 converge, avg 1.14 rounds**. A live demo with two independent Sonnet subagents (spec-only, no code access) produced a real 3-turn exchange that decodes cleanly — and caught a real spec ambiguity (multi-value candidates) on the first attempt, fixed and re-verified. Full design rationale, the round-cap bug, and honest scope limits (not yet a live multi-round autonomous exchange, not yet wired into the CLI): `BENCHMARK/PREREG_0.3.md` (E-NEGOTIATE) and `data/negotiation/live_demo_transcript.md`. Wired into the CLI/API 2026-09-30: `aixl.negotiate`/`aixl.negotiate_aixl` (same pattern as `compare`/`compare_aixl`), `python cli.py negotiate SENDER RECEIVER [--rounds N] [--json]` / `negotiate-aixl`. Testing the real CLI output (not any unit test) caught a second bug: the CLARIFY turn's candidates/question had receiver and sender swapped in the DISPLAYED wording (the resolved value was always correct regardless) — fixed. Reproduce: `python -m benchmarks.negotiation_eval` or `python cli.py negotiate "Close ticket #77." "Delete ticket #77."`.

## 12. Real protocol adapter E-MCP (2026-09-30)
Everything up to this point (comparator, drift, negotiation) never touched a real external transport — `aixl/adapters/protocol_adapter.py`'s `MCPAdapter` raised `NotImplementedError`. Built it for real, against the official `mcp` Python SDK (package `mcp` 2.2.0, MCP spec 2025-06-18) instead of guessing the wire shape: `MCPAdapter.validate()` runs a payload through the SDK's own pydantic models, so a malformed envelope is caught by the real spec's rules. Went further than the adapter alone: `aixl/mcp_server.py` is an actual running MCP server (stdio transport) exposing `aixl_translate`/`aixl_compare`/`aixl_negotiate` over the real protocol. **Real validation, not a mock**: `tests/test_mcp_integration.py` spawns the server as an actual OS subprocess and drives it with the SDK's own client over real stdio JSON-RPC — 4/4 pass, including `aixl_negotiate` converging on the same "Close/Delete ticket #77" case from the E-NEGOTIATE live demo, this time over a real transport instead of two human-relayed subagents. 13 new tests (9 adapter + 4 integration), 139/139 total. `mcp` is an optional dependency (`pip install .[mcp]`) — the core suite never requires it (integration tests skip cleanly if absent). **Third-party client confirmed the same day**: registered the server in Claude Desktop's own `claude_desktop_config.json` (`mcpServers.aixl-core`); the user restarted the app and called `aixl_compare` from an ordinary chat conversation — a genuine, independently-built MCP client, not this project's test suite. Result matched exactly (NOT equivalent, CRITICAL_DRIFT, NEGATION difference), reproduced immediately after from this separate Code session and frozen in `BENCHMARK/results_mcp_desktop_client_FIRST_RUN.md`. **`aixl_negotiate` confirmed too, same session**: user ran the "Close/Delete ticket #77" case; transcript matched this project's own reproduction exactly, frozen in `BENCHMARK/results_mcp_desktop_negotiate_FIRST_RUN.md`. That same test also surfaced a real design gap, **fixed the same day**: `negotiate()`'s ANSWER turn re-derives from the sender's already-computed canonical value rather than a live re-confirmation, and a constructed case (`aixl_negotiate("Quita el ticket #77.", "Elimina el ticket #77.")`, "quita" outside the vocabulary) showed it could report ACCEPT/converged while silently discarding the receiver's plausibly-correct reading. Fixed by rejecting instead, scoped narrowly to `actions` (the one dimension where empty is always a failure, never a legitimate answer) — a broader first attempt broke a real case where an empty `negation` value was the correct resolution, caught immediately by the test suite. Re-verified: the ambiguous case now REJECTs, "Close/Delete ticket #77" still ACCEPTs, and the real 21/21 E-INTEROP convergence measurement is unaffected. 2 new regression tests, 141/141 total. See LIMITATIONS.md for the residual scope. **`aixl_translate` confirmed too**: user ran "Analiza las ventas del primer trimestre de 2026." — output matched this project's own reproduction exactly, frozen in `BENCHMARK/results_mcp_desktop_translate_FIRST_RUN.md`. All 3 exposed tools are now confirmed with this real third-party client. **A SECOND, independent vendor's client confirmed too**: registered the same server in OpenAI's ChatGPT/Codex desktop app (`~/.codex/config.toml`, `[mcp_servers.aixl-core]` — a completely separate config format/codebase from Claude Desktop's), user restarted it and called `aixl_compare` from an ordinary conversation — result matched exactly, frozen in `BENCHMARK/results_mcp_second_client_codex_FIRST_RUN.md`. Two independent vendors' clients (Anthropic's Claude Desktop, OpenAI's ChatGPT/Codex) now both interoperate with this server correctly. **A THIRD vendor confirmed too**: Gemini Desktop's UI has no path to add custom MCP servers (checked exhaustively); `gemini-cli`'s personal Google OAuth login turned out to be server-side discontinued mid-project ("migrate to the Antigravity suite of products"); followed that pointer, installed Google's newer **Antigravity CLI** (`agy`), registered the server (`agy mcp add`), and the user ran a real chat prompt there — Antigravity's own agent found and called `aixl-core/aixl_compare` (with a genuine tool-approval gate) and returned the correct result, matching this project's reproduction exactly, frozen in `BENCHMARK/results_mcp_third_client_antigravity_FIRST_RUN.md`. Three independent vendors (Anthropic, OpenAI, Google) now confirmed. **`aixl_negotiate` AND `aixl_translate` confirmed on Antigravity too, same session**: the user's agent called both, matching this project's own reproductions exactly (`BENCHMARK/results_mcp_third_client_antigravity_FIRST_RUN.md`) — all 3 tools now on Antigravity, same coverage as Claude Desktop. **Then the same on Codex**: the user ran `aixl_negotiate` and `aixl_translate` there too, both matching exactly (`BENCHMARK/results_mcp_second_client_codex_FIRST_RUN.md`). **All 3 tools are now confirmed on all 3 independent vendor clients** (Anthropic, OpenAI, Google) — a real, broad, cross-vendor interoperability result, not a single lucky case. ## 13. Autonomous 2-process negotiation, no human relay: E-AUTONOMOUS (2026-09-30)
The single most-repeated "still not done" line across E-NEGOTIATE and every E-MCP third-party test: nothing had two SEPARATE, independently-running processes exchange real NEGOTIATE turns with zero human involvement. Built `aixl/agents/sender_agent.py` — a REAL, standalone MCP server (its own OS process) that answers CLARIFY questions **recomputed fresh from its own stored source on every call**, never a value cached at setup — and `aixl/autonomous_negotiation.py`'s `negotiate_autonomous()`, which spawns it as a genuine subprocess and drives the same turn semantics as `aixl/negotiation.py` (imported, not reimplemented; `negotiate()` itself is completely untouched, its 141 tests keep passing unmodified). **Real validation**: `tests/test_autonomous_negotiation.py` (5 tests) proves parity with `negotiate()` on the same inputs, confirms the REQUEST turn now carries a genuinely transmitted AIXL payload (unlike `negotiate()`'s, which never needed one), and confirms the REJECT-on-empty-actions case still holds. **Re-measured the real 21 E-INTEROP disagreements through two genuinely separate OS processes** (`benchmarks/autonomous_negotiation_eval.py`): **21/21 converge, avg 1.143 rounds** — identical to the single-process measurement, now via real subprocess-to-subprocess MCP stdio JSON-RPC, no shared memory, no human touching a turn. (This 21/21 number was later revised to 20/21 by §14's destructive-action fix — see there for why that's a correction, not a regression.) 5 new tests, 146/146 total. Honest scope: for the 21 replayed cases the sender answers from an already-fixed AIXL line, so "live" there means real process/transport separation, not fresh natural-language re-interpretation (that liveness is demonstrated only on the smaller `--text`-mode cases); the sender is still trusted as authoritative, same as `negotiate()`; only one sender + one receiver shown, not yet two full peer AIXL instances. **Wired into the real MCP server the same day**: `aixl_negotiate_autonomous` added to `aixl/mcp_server.py` — calling this ONE tool over real MCP stdio makes the server spawn a genuinely separate sender-agent subprocess (a THIRD process) and negotiate with it, so a real MCP client can trigger the full autonomous exchange itself. Verified with the SDK's own client and a new subprocess-based integration test (147/147 total). Still open: not yet called from a real deployed client (Claude Desktop/Codex/Antigravity) — only from this project's own test client so far. Full design detail: `BENCHMARK/PREREG_0.3.md` (E-AUTONOMOUS). Reproduce: `python -m pytest tests/test_autonomous_negotiation.py -q` or `python -m benchmarks.autonomous_negotiation_eval`.

## 14. Negotiation must escalate destructive-action disagreements: E-MCP-DESTRUCTIVE (2026-09-30)
The user retested `aixl_negotiate_autonomous` from real Claude Desktop with §13's env/cwd fix in place — **it converged correctly**, confirming that bug. But the same test then raised a real concern unprompted: "Close ticket #77." (UPDATE) vs "Delete ticket #77." (DELETE) converged in 1 round trusting the sender, with no signal that DELETE — the losing candidate — is irreversible, even though `aixl_compare` on the same pair already flags CRITICAL_DRIFT/"destructive action involved". Confirmed systematic with 3 real pairs (Close/Delete, Archive/Delete, Send/Delete — all showed the same pattern), not a one-off.
First fix (reuse comparator's `destructive_actions`: DELETE/EXECUTE/SEND/DISABLE/UPDATE) broke 8 existing tests immediately — UPDATE is on that list and appears in countless ordinary disagreements, including the project's own long-standing Close/Delete reference case. Caught by the full suite before shipping. Narrowed to a NEW, separate `data/config.json` key, `irreversible_actions` (DELETE only) — `destructive_actions` stays as-is for comparator's own severity display. Applied in both `negotiate()` and `negotiate_autonomous_async()`.
**Re-measured the real 21 E-INTEROP disagreements**: now **20/21 converge** (was 21/21) — the one that now REJECTs, `t061` ("É permitido excluir o evento #40."), is a genuine case where Gemini misread "excluir" (EXCLUDE, reversible) as DELETE (permanent); the old 21/21 number had been silently trusting Sonnet's correct reading with no way to tell it apart from a case where the sender itself was wrong. This is a correction, not a regression. 12 new/changed tests, 152/152 total.
**Widened to EXECUTE and SEND at the user's request, same day**: fixed 4 more tests that used SEND as a "still reversible" example, added 2 REJECT tests, 154/154 total. Re-measured: now **18/21 converge**. Individually examined the 3 REJECTs, not just counted: SEND's addition caught a genuine bug (`t092` — Gemini over-extracted SEND from a temporal clause, "before sending it"); EXECUTE's addition is more debatable (`t077` — "schedule the call" mapped to EXECUTE by one vendor and UPDATE by the other, but scheduling isn't genuinely irreversible under either reading — a translator vocabulary quirk, not real evidence EXECUTE-involving disagreements are dangerous). Reported honestly rather than declared settled.
**Wider evidence search confirmed the split**: scanned an independent, larger corpus (the 200-pair E-XV cross-vendor dataset, 400 texts) — 8 of 10 total real EXECUTE-disagreement instances (across both datasets) turned out to be the same translator-vocabulary quirk ("execute/run the analysis" mistagged as EXECUTE instead of the real, benign action ANALYZE); SEND found 2 MORE real, distinct supporting cases in that same search. **Removed EXECUTE, kept SEND and DELETE.** Re-measured one final time: **19/21 converge** (was 18/21) — exactly the 2 cases with real evidence now REJECT, zero false positives remain. Full design detail and the full evidence breakdown: `BENCHMARK/PREREG_0.3.md` (E-MCP-DESTRUCTIVE) and `BENCHMARK/results_irreversible_actions_evidence_search.md`.
