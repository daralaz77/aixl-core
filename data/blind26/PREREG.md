# blind26 (80 pairs) — pre-registration, written 2026-11-06 BEFORE the pairs exist
Purpose: first fresh test of the COMBINATION "rule comparator says EQUIVALENT AND two LLM judges both say SAME". On blind19-25 (all spent) this rule left 2 false accepts of 342 (comparator alone 16, judges alone 24 by both-SAME); comparator and judge errors overlapped in only 2 pairs. That was development evidence; this set is the real test.
Code frozen at git commit 31696d7 (v0.6.0 plus the docker-publish change; `git status aixl/` clean). Full hashes go into CODE_FREEZE.json before the judges run.

Families: ALL NEW, none among the 81 used in blind2-blind25: persistence_one_off_vs_standing, agent_vs_delegation, default_vs_override, object_granularity (file / folder / repository, row / table / database), report_vs_perform (confirm / say vs do), output_format_language (reply language, file format), visibility_confidentiality (privately / publicly / who can see), preview_vs_commit (draft / dry run / simulate vs send / apply / execute), entity_disambiguation (same name, different entity), failure_handling (if it fails: retry / stop / skip / report). Chosen because they are about what an agent will actually DO, the use AIXL is meant for.
Authors: two fresh agents (Opus and Sonnet), 40 pairs each, 4 per family per author, about 40 / 40 / 20 EQUIVALENT / NOT_EQUIVALENT / UNDECIDABLE, es / en / pt mixed. They get nothing about AIXL, its code, or any result; only the family list, the label definitions and the schema. Ids R001-R040 (Opus), S001-S040 (Sonnet). Authors write their file themselves with the Write tool, to one given path, no other file.

Systems measured (fixed now):
- R0 comparator alone: `compare_texts(a, b)` verdict EQUIVALENT = accept.
- R1 (PRIMARY): comparator EQUIVALENT AND both judges SAME.
- R2 (reported): `compare_texts(a, b, strict=True)` EQUIVALENT AND both judges SAME.
- Judges alone: each judge SAME; both SAME.
Judges: two fresh agents (Opus, Sonnet), separate contexts, different from the authors, `aixl/resources/arbiter_rules_v1.txt` verbatim as the prompt, pairs anonymised and shuffled (ids Q001-Q080, no labels, no family), one pass, prompt not changed after seeing results.

Gates:
  G1 (decides the claim): R1 false accepts <= 3% of the non-EQUIVALENT-labelled pairs (UNDECIDABLE included). With about 48 such pairs that means at most 1. Every id listed.
  Reported next to it, always: R0, R2, judges-alone false accepts; proven-EQUIVALENT recall of R1 (a rule that accepts nothing also passes G1); error overlap between comparator and judges and between the two judges; per-family table.
Claim policy: if G1 passes, the only claim allowed is narrow: "on 80 pairs by two new authors in 10 new families, comparator AND two judges accepted 0 or 1 of N non-equivalent pairs", with the proven-EQUIVALENT recall next to it and this sentence: a passing 0 of 48 has a 95% upper bound of about 6% (rule of three), so it does NOT prove <= 3%, and one passing set after earlier failures is weak evidence. If G1 fails the finding is "the combination is not reliable outside the tuned constructions".
Labels are the authors' and are NOT corrected; disputed labels are listed with both readings and gates use the original labels. One run on the frozen code; the evaluator refuses a second run and refuses if code or pair files changed. The result file is written with an editor tool after capturing stdout.
Expectation written beforehand: R0 alone will fail G1 again (>= 2 false accepts); judges alone 5-10% false-SAME; R1 0-2 false accepts; R1 proven-EQUIVALENT recall under 15%. If R1 shows 2 or more, the deployment advice stays "do not claim no-silent-failure".
Honest limits written beforehand: authors and judges are all Claude models (the same family can share blind spots and the error overlap I measured between the two judges is high); labels come from models, not humans; 80 pairs give a wide interval; with proven-EQUIVALENT recall near zero, G1 passing says a lot about fail-closed behaviour and little about meaning.
